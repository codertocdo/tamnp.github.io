In our journey through data structures, we have encountered various paradigms for storing and retrieving memory. Linear structures like standard <span class = "txt-basic">Arrays</span> provide contiguous memory layouts for lightning-fast indexing, but the degrade to a sluggish $O(n)$ linear scan when <span class = "txt-operation">searching</span> for a specific key. <span class = "txt-basic">Linked Lists</span> solve the problem of dynamic allocation but force the CPU into inefficient, $O(n)$ pointer-chasing.

Even as we leveled up to complex, self-balancing hierarchical structures like the [B-Tree]({% post_url 2026-05-29-btree%}), we hit a mathematical ceiling. Their retrieval time is inherently bottlenecked at $O(\log n)$ because they strictly rely on *key comparisions* (evaluating whether to branch left or right). As datasets scale to millions of records, this traversal still incurs a heavy computational cost.

To shatter this logarithmic barrier and achieve a constant time complexity of $O(1)$ for key-based searching, we must abandon comparisons altogether. Instead, we use mathematics to map a <span class = "txt-highlight">Key</span> directly to a physical Memory Address. The data structure that performs this magic is the <span class = "txt-special">Hash Table</span>.

## 1. The Mathematical Foundation: Modular Arithmetic

Before we can understand how a hash function works, we need to appreciate the math behind it. Hash functions heavily rely on **modular arithmetic**, also known as **congruence theory**.

### What is Congruence?

**Definition:** Given a positive interger $n \in \mathbb{N}$, two intergers $a, b \in \mathbb{Z}$ are said to be **congruent modulo** $n$ if they have the same remainder when divided by $n$.

$$a \equiv b \pmod{n}$$

**Examples:**

* $11 \equiv 8 \pmod{3}$, because both 11 and 8 leave a remainder of 2 when divided by 3.
* $-2 \equiv 5 \pmod{7}$, because both leave a remainder of 5 when divided by 7.

The congruence relation is an **equivalence relation**, satisfying three key properties:

| Property         | Statement                                                           |
| ---------------- | ------------------------------------------------------------------- |
| **Reflexivity**  | $a \equiv a \pmod{n}$                                               |
| **Symmetry**     | $a \equiv b \pmod{n} \implies b \equiv a \pmod{n}$                  |
| **Transitivity** | $a \equiv b$ and $b \equiv c \pmod{n} \implies a \equiv c \pmod{n}$ |

### Arithmetic on Congruences

If $a_1 \equiv b_1 \pmod{n}$ and $a_2 \equiv b_2 \pmod{n}$, then all the following hold:
 
$$a_1 + a_2 \equiv b_1 + b_2 \pmod{n}$$
$$a_1 - a_2 \equiv b_1 - b_2 \pmod{n}$$
$$a_1 \cdot a_2 \equiv b_1 \cdot b_2 \pmod{n}$$
$$a_1^k \equiv b_1^k \pmod{n}$$

These rules let us *reduce* large computations modulo $n$ at every step - a critical technique for efficient hashing.

## 2. Hash Tables: Core Concepts

### What is a Hash Table?

**Hash Table** is a data structure that stores elements at addressed positions. Typically implemented as an array of $m$ slots indexed from $0$ to $m - 1$.

**Hash Function** is a mapping from a universe of keys $U$ to table addresses:

$$h : U \to \{0, 1, \ldots, m-1\}, \quad k \mapsto h(k)$$

The value of $h(k)$ is called the **hash code** (or simply the **address**) of key $k$.

### Load Factor and Collision

**Load Factor** is the ratio of stored elements $n = |U|$ to table size $m$:

$$\alpha = \frac{n}{m}$$

The load factor is the single most important parameter for hash table performance. When $\alpha$ is low, the table is spares and collisions are rare. As $\alpha$ approaches 1 (or exceeds it), performance degrades rapidly.

**Collision** is a phenomenon of two (or more) keys being hashed into the same cell of the hash table. Two distinct keys $x \neq y$ are said to **collide** if $h(x) = h(y)$.

Collisions are mathematically inevitable whenever $|U| > m$ (the pigeonhole principle guarantees it). The entire art of hash table design is about *minimizing* collision probability and *handling* collisions gracefully when they occur.

The collision probability for a randomly chosen hash function is denoted $\Pr[h(x) = h(y)]$.

## 3. Designing a Good Hash Function

### Requirements of a Good Hash Function

A well-designed hash function must satisfy three criteria:

1. **Deterministic:** The same key always produces the same hash code $h(k)$.
2. **Low collision probability:** Keys are distributed uniformly across all $m$ slots.
3. **Fast to compute:** Ideally $O(1)$ time per hash computation.

### Key Type Conversion

Hash functions operate on **usigned intergers**. If your key is not already an integer, you must convert it first:

* **Float → String:** `12345.27 → "12345.27"`, then hash the string representation.
* **String → Integer:** Interpret the raw bytes as a multi-byte integer. For example, `"AB"` → `0100 0001 0100 0010` (ASCII bits) → `16706`.

**Type-Conversion Hash:** A function $f: S \to \{0, 1, \ldots, 2^n - 1\}$ that maps a string $s$ to an unsigned integer $f(s)$.

#### Well-known Type-Conversion Functions

| Function            | Output Size     | Notes                                           |
| ------------------- | --------------- | ----------------------------------------------- |
| **CRC32**           | 32-bit integer  | Checksum; primarily for data integrity          |
| **MD5**             | 128-bit integer | Widely used; no longer cryptographically secure |
| **SHA-1**           | 160-bit integer | Deprecated for security use                     |
| **SHA-2** (SHA-256) | 256-bit integer | Modern standard; cryptographically secure       |

## 4. Collision Resolution

### Overview

Every hash table implementations must answer the question: *what happens when two keys land on the same slot?* There are three principal strategies:

1. **Seperate Chaining** - chain colliding elements in linked lists.
2. **Open Addressing** - probe for an alternative empty slot within the table.
3. **Perfect Hashing** - use two-level hashing for guaranteed collision-free lookup.

### Strategy 1: Seperate Chaining

**Idea:** Each table slot holds a pointer to a linked list of all elements that hash to that index. Collisions simply append to the list.

### Strategy 2: Open Addressing

In seperate chaining, many table slots may remain empty while others hold long chains - plus you pay a memory penalty for every linked-list pointer. **Open addressing** stores all elements *inside* the table itself, eliminating auxiliary memory.

The key idea: instead of one hash function, we use a **probing sequence** $h_0(x), h_1(x), \ldots, h_{m-1}(x)$ — a permutation of $\{0, 1, \ldots, m-1\}$ — and store the key in the first empty slot we encounter.

### Strategy 3: Perfect Hashing

Both chaining and open addressing accpet *some* probability of collisions. **Perfect Hashing** eliminates collisions entirely for a *static* (unchanging) key set by using a two-level hash table.

**Phase 1:** Apply $h(x)$ to distribute all $n$ keys into $m$ rows of a 2D table $T$. Count $C[i]$ = number of keys landing in row $i$.

**Phase 2:** For each row $i$, allocate exactly $C[i]^2$ slots. Apply a second hash function $g(x)$ to scatter the row's elements into those slots. With $C[i]^2$ slots available, a randomly chosen $g$ produces zero collisions with constant probability - and if a collision does occur, simply pick a new $g$ and retry.

The hash function acts as a mapping mechanism from a universe of keys $U$ to a specific address: $h: U \to \{0, 1, \dots, m-1\}$[cite: 83].

2. [cite_start]<span class="txt-highlight">Uniform Distribution:</span> It should distribute keys evenly across the addresses to minimize collisions[cite: 162].

### Typecasting and Hashing Algorithms
[cite_start]Since hash functions perform mathematical operations, all keys (like strings) must be converted into unsigned integers[cite: 122].

* **For Strings (Polynomial Hashing):** Let $s$ be a string of length $m$ and $b$ be a constant base. The hash is calculated as:
  [cite_start]$f(s) = (s_0 \cdot b^{m-1} + s_1 \cdot b^{m-2} + \dots + s_{m-1}) \pmod{2^n}$[cite: 152, 153].

  [cite_start]The optimal value for $A$ is the golden ratio: $A = (\sqrt{5} - 1) / 2 \approx 0.618033$[cite: 195].

## 2. Mathematical anatomy of a B-Tree

### Properties of a B-Tree

A <span class="txt-highlight">B-Tree</span> of order $m$ is a highly constrained m-Way Search Tree. To guarantee structural balance ($O(\log m)$ time complexity), it must satisfy strict mathematical invariants:

1. <span class = "txt-highlight">Root Constraint:</span> The root must have at least 2 children (unless it is a leaf).
2. <span class = "txt-highlight">Node Capacity Limits:</span>
   * Every node has at most $m$ children and $m-1$ keys.
   * Every internal node (except the root) must be at least half-full. It must have at least $\lceil m/2 \rceil$ children and $\lceil m/2 \rceil - 1$ keys.
3. <span class = "txt-highlight">Perfect Leaf Alignment:</span> All leaf nodes must exist strictly at the exact **same level**. This property is what defines it as "perfectly balanced".

Following is an example of a B-Tree of order 4:

We can see in the above diagram that all the leaf nodes are at the same level and all non-leaf nodes have no empty sub-tree and have number of keys one less than the number of their children.

### B-Tree's Height theorems

The absolute guarantee of a B-Tree's performance lies in its <span class = "txt-highlight">height</span> bounds. Let $n$ be the total number of keys in a B-Tree of order $m$ and height $h$ (assuming the root is at level 1). Let the minimum degree be $t = \lceil m/2 \rceil$.

1. <span class = "txt-highlight">Minimum Height:</span> The tree is as flat as possible when every node is completely saturated with $m - 1$ keys. The height is bounded by:

$$h \ge \log_m(n+1)$$

2. <span class = "txt-highlight">Maximum Height:</span> The tree is as tall as possible when every internal node contains the bare minimum of keys ($t - 1$). By summing the nodes at each level, mathematicians have proven the upper bound:

$$h \le \log_t \left( \frac{n+1}{2} \right) + 1$$

These theorems mathematically prove that the height grows **logarithmically**.

## 3. Operation in B-Tree

### Searching

<span class = "txt-highlight">Searching</span> in a B-Tree is a two-tier process that beautifully balances fast CPU operations with slow Disk I/O.

When looking for a target key $X$, starting from the root:

1. <span class = "txt-highlight">In-Memory Binary Search:</span> Once a node (a disk page) is loaded into RAM, we perform a standard <span class = "txt-basic">Binary Search</span> within its sorted `keys` array. Because this happens entirely in the CPU cache, it is blindingly fast.
2. <span class = "txt-highlight">Evaluation:</span>
   * If $X$ matches a key, the search terminates successfully.
   * If $X$ is not found, the binary search gives us the correct routing index $i$ where $k_{i-1} < X < k_i$.
3. <span class="txt-highlight">Disk Traversal:</span> We look at the pointer $P_i$. If the current node's `isleaf` flag is `true`, the pointer is `nullptr` and the key does not exist. Otherwise, we command the hardware to fetch the child node $P_i$ from the disk into RAM, and recursively repeat the process.

### Insertion

Unlike a <span class="txt-basic">Binary Search Tree</span> that growns downwards, a <span class="txt-highlight">B-Tree growns upwards</span>.

When inserting a new key $X$:
1. Traverse down to the appropriate leaf node.
2. If the leaf is not full, insert $X$ into the array. 
3. <span class="txt-highlight">The Split:</span> If the leaf is full (an overflow condition), we temporarily insert $X$ to find the median key. The node is violently split into two halves.
4. <span class="txt-highlight">Promotion:</span> The median key is stricly pushed up to the parent node. If the parent is also full, the split cascades upwards. If the root splits, a new root is created, increasing the height by 1.

### Deletion

Deletion might cause a node to fall below its minimum threshold. This triggers an underflow state.

The rescue operation has two phase:
1. <span class="txt-highlight">Borrowing:</span> The deficient node looks to its immediate sibling. If a sibling has spare keys, we perform a rotation: pull a key from the sibling up to the parent, and pull the parent's separating key down.
2. <span class="txt-highlight">Merging:</span> If both siblings are at minimum capacity, we merge the deficient node, its sibling, and the separating key from the parent into a single node. This removes a key from parent, potentially causing the parent to underflow, cascading the deletion upwards.
